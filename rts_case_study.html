How I Direct an AI Coding Agent to Ship Production Software

RouteToServe: a real app, real users, a real incident — and the spec-driven process behind it.

The Problem

Built for the office, not the field

I've worked as a process server since 2025 — serving legal documents across multiple stops a day, tracking chain-of-custody, hitting filing deadlines. Within a few weeks I could already see what was missing: the tools that existed gathered information about a route after the fact, instead of actually supporting the person driving it. No route optimization, no offline-first attempt logging, no real reconciliation between what got served, mailed, or returned and what the pay should be.

Nobody was going to build the tool that fixed this for the field side. So I built it myself — self-taught, through two earlier iterations before arriving at what exists now. Not by learning to write production code from scratch, but by learning to direct the people, and increasingly the AI, who could.

The Approach

Spec-driven development

RouteToServe is a React/Vite mobile app running on Base44, synced to GitHub. I own the product end-to-end — architecture, roadmap, brand, database schema — but I don't write the code myself. Early on I wrote every instruction from scratch by hand, re-explaining the same guardrails every time. Since then that discipline has become an actual workflow: a system that carries the rules for me, so I'm directing the work instead of re-deriving the process on every change.

  • I talk through what needs to happen in plain conversation — not a rigid template. I describe the problem the way I'd explain it to a person.
  • The system turns that into a structured, auditable spec automatically — guardrails, file scope, "what does done look like" all carried in from a standing rule set, not retyped every time.
  • An AI coding agent (Claude) executes against that spec through a written handoff document — an auditable contract, not a loose back-and-forth lost in a chat log.
  • The agent audits before it builds — reads the real files fresh, reports what it found, holds for approval before touching anything.
  • I review and approve every change before it ships. Nothing reaches production without passing gates: linting, dependency-cruiser checks, duplicate-code detection, and custom audit checks that block entire known bug classes from ever landing again.

That last point is the part that actually proves the process works. Here's a real example.

A Real Incident

The role-enum bug

Base44, the platform RouteToServe runs on, has a User.role field. I assumed — reasonably, based on how the app was designed — that it supported values like 'admin', 'user', 'server', 'boss', and 'worker'. Most of the early role-based logic in the app was written comparing against those values.

It actually only ever supports two: 'admin' and 'user'. Every comparison like role === 'server' was silently, permanently false — it could never evaluate true, no matter what. This wasn't a typo or an edge case. It was a wrong assumption baked into the foundation, and it produced two separate production incidents months apart.

Incident one

A serve-write guard silently failed for real users.

Incident two

An entire background sync engine never activated for anyone, on any account, because the mount condition checked a role value that could never match.

The fix wasn't just patching the two bugs — that would've left the same landmine in the ground for the next feature.

1 — Diagnose fully

Root cause confirmed in code before any fix was written: the specific field, the specific values, the specific reason the comparison could never be true.

2 — Canonical source

Built two predicate functions — isAdminUser, isFieldWorker — as the one true source for role logic. No other file may duplicate the check.

3 — Automated gate

Added a grep-based audit that runs before every push and hard-blocks any code comparing against a banned role literal like 'server' or 'boss'. Not a style guideline — a gate that fails the build.

That bug class hasn't recurred — because the system no longer allows the mistake that caused it, not because everyone just remembered to be careful.

What a Real Spec Looks Like

An actual handoff, lightly trimmed

What I actually said to kick it off

"The [sync banner] doesn't work. We have tried it and it doesn't work like we want it to. Honestly the banner should just be moved to the settings screen so that way we know there is nothing covering it and we can click it if need be from there."

Type

BUILD. Two labeled commits, commit-and-hold — report SHAs + gate exit codes, push nothing until I say "push it."

Why

The home-screen sync banner has been a recurring pain point — intermittently false counts, a Retry tap that got swallowed, no way to inspect the parked data from the installed mobile app. My decision: sync surfacing leaves the home screen entirely, and Settings gains a section that's both the control surface and the field evidence tool.

Guardrails

UNTOUCHABLE: the outbox drain engine, the blob store, the attempt actions, and the evidence capture logic — all off-limits except one explicitly permitted read-only export. This build surfaces sync truth; it does not change sync behavior. No opportunistic fixes, however obvious once the data's visible. No new dependencies. Anything outside the settings screen and the one permitted export → stop and ask, don't improvise.

Output

Two labeled commits, gate results (audit exit 0, build exit 0, lint at baseline), report: SHAs, line counts of touched files, confirmation home renders zero sync UI. Hold for my "push it."

That's what "spec-driven" actually means in practice — not a vague ask, a written contract with explicit boundaries, a stated reason, and a defined shape for what "done" has to prove.

Day to Day

The patterns that hold it together

  • One true source, no duplication. Canonical logic for pay calculation, address validation, name matching, and role checks each live in exactly one place.
  • Diagnostic-first, always. The agent audits and reports before it edits, every time. If two attempts at a fix fail, we stop and revert rather than guessing a third time.
  • Field-verify after push, never before. The app only runs by pulling from GitHub through Base44 — so testing locally proves nothing about what a real user will experience. Not "done" until confirmed against production, on the actual device, in the field.
  • File-size and complexity limits, enforced not aspirational. Once a component crosses its ceiling, it gets split before more gets added.
  • Offline-first is unconditional. Every user action writes locally first with instant confirmation, then syncs in the background. A dead cell signal can't be allowed to lose someone's work.
  • The system verifies its own work. After any write that matters, the process reads the file back and confirms the change actually landed — closing the gap where an AI agent can report success when it didn't.

The Result

In daily production use

RouteToServe runs real routes for me daily, and for a second user, Dawn — a veteran process server who runs roughly three times my volume through the same system. It handles route optimization, offline-first attempt logging, payroll reconciliation, and document tracking, with a real incident history, a real audit trail, and a real roadmap I manage.
